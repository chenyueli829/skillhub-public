# 02 案例库：复杂决策拆解

## 案例 1：选型 — 企业该用 WorkBuddy 还是深化现有协同平台 AI？

**背景**：一家 500 人科技公司，已用飞书 3 年，考虑引入 WorkBuddy 做跨工具调研与交付。

**决策点**：
- 核心 Job 是「知识工作」还是「跨生态工具编排」？
- 是否愿意引入第二套工作台 vs 深化飞书 Aily + CLI？

**拆解**：
| 选项 | 优势 | 代价 | 适用 |
|------|------|------|------|
| 深化飞书 Aily | 零迁移、上下文在飞书内 | 跨 GitHub/Jira 弱 | 文档协作为主 |
| 引入 WorkBuddy | MCP 跨工具、Expert 库 | 双平台、身份同步 | 跨工具交付物生产 |
| 自建 Agent | 完全定制 | 工程与治理成本高 | 有 Agent 团队 |

**资深判断**：若 Job 是「从多源调研到 PPT 交付」，WorkBuddy 有优势；若 Job 是「飞书内知识沉淀」，优先 Aily。可并行 POC 2 周比选型会。

**来源**：竞品对比见 `research/research-report.md` §1.2

## 案例 2：治理 — 调研报告 Agent 要不要自动发送？

**背景**：WorkBuddy 生成竞品报告后，用户希望「一键发全员邮件」。

**风险**：未审核的幻觉数据、竞品误读、合规问题。

**资深方案**：
1. 强制 HITL：发送前人工勾选「已核实来源」
2. 输出分层：内部草稿（可激进）vs 对外版（必须引用）
3. 审计：记录 prompt、来源 URL、修改人

**反模式**：为了「炫技」去掉人审，用全自动发送。

## 案例 3：编排 — 深度调研要不要拆 Team？

**背景**：用户要「行业报告 + 数据表格 + 执行摘要 PPT」。

**拆解**：
- Agent A：深研与引用（类似 ecc-deep-research）
- Agent B：结构化表格与指标
- Agent C：叙事与 PPT 大纲
- Lead：合并、去重、一致性检查

**WorkBuddy 映射**：Expert Teams 模式；本仓库可拆为多个 Skill 串联。

**失败模式**：单 Agent 一次生成全部 → 表格与叙事不一致。

## 案例 4：组织 — 超级个体陷阱

**背景**：公司 10 个「Agent 高手」，但知识不共享、Prompt 各自为政。

**症状**：产出质量方差大、无法审计、离职带走工作流。

**资深干预**：
1. 建立共享 Skill 库与评审流程
2. Enterprise OneID + 积分计量对齐成本意识
3. 模板化 Identity/SOUL，禁止个人野路子连接生产数据

**来源**：WorkBuddy Enterprise 发布叙事（research-report §1.1）
